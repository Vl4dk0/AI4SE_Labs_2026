Embedding matching is a poor fit. The task already names the file, class, and method, and the tests are the specification. Similarity spends a fixed budget on text that looks like the query.

In the sanity check the empty stub ranked 1, 2, and 3 for `is_terminal`, `__contains__`, and `Order.__len__`. The query is the signature and docstring; the stub is that plus `pass`. A fixed top 5 burns a slot on a chunk with no behaviour. Filtering it afterwards is a patch, not a better search.

A larger k does not fix the misses we measured. For `Order.__len__` the top 5 were `OrderBuilder.__len__`, `OrderLog.__len__`, the stub, the `OrderLog` header, and the module header. The `Order` header was absent. The method still passed. For `__contains__` the query says "positive on-hand stock", so the neighbours are unknown-SKU tests, not the zero-on-hand test. More hits from that ranking still follow the docstring. Ranks past the five we sent were not logged, so "use 10" is a guess.

Splitting was not the failure. One chunk per method, plus a class header of signatures and attributes, matched these tasks (longest chunk 1943 characters; the 1500-token split never ran). The `OrderStateMachine` header is the right grain: it carries `TRANSITIONS`. The miss is edges between chunks: that header has neither `Money`'s fields nor the exception a caller expects.
